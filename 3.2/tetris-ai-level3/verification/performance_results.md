# 성능 측정 결과

측정 환경: Windows 11 Home · Intel Core i7-8700 3.2 GHz · RAM 32 GB · Python 3.12.4  
측정일: 2026-11-16 · 모든 수치는 `verification/*.json`의 실제 측정값이며 이 문서는 `make_reports.py`가 자동 생성합니다.

## 1. AI 탐색 시간 (개선 전·후 동일 입력)

- 입력: 정상 AI로 5개 시드(3, 11, 29, 47, 83)를 진행하며 3블록마다 저장한 **고정 보드 100개** (`bench_boards.json`)
- 방법: 각 보드에서 `choose()` 1회 호출 시간, 보드당 3회 반복(난이도별 300회), 캐시를 매번 비운 **콜드 측정**
- 도구: `python verification/bench_ai.py <프로젝트 폴더> verification/bench_boards.json <결과.json>`

| 난이도 | 개선 전 평균 | 개선 전 p95 | 개선 전 최대 | 개선 후 평균 | 개선 후 p95 | 개선 후 최대 | 평균 기준 배수 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 쉬움 | 36.39 ms | 67.6 ms | 75.07 ms | 2.23 ms | 4.61 ms | 7.73 ms | 16.3배 |
| 보통 | 36.35 ms | 66.46 ms | 82.96 ms | 2.14 ms | 4.32 ms | 6.09 ms | 17.0배 |
| 어려움 | 859.09 ms | 2084.33 ms | 2440.8 ms | 49.51 ms | 119.91 ms | 187.95 ms | 17.4배 |

**정확도 유지 확인:** `check_ai_equivalence.py`로 같은 300개 사례(보드 100 × 난이도 3)에서 원본과 최적화 AI의 **전체 후보 순위와 점수가 300/300 동일**(점수 차 최대 0.0)함을 확인했습니다. 또한 `tests/test_ai_extra.py`가 원본 알고리즘을 그대로 옮긴 참조 구현과 결과를 비교합니다.

최적화 내용: 회전별 블록 좌표 사전 계산, 보드를 20개 행 비트마스크로 변환, 열 높이로 낙하 위치를 한 번에 계산, 이동 전 보드 평가(높이·구멍·T-Spin 후보)를 탐색당 1회만 계산, 결과 LRU 캐시(512개), 백그라운드 작업 스레드.

## 2. GUI 응답성 (실제 Tk 창, 개선 전·후 동일 부하)

- 부하: 인간 vs AI 모드, AI 도우미 켬, 150 ms마다 합성 키 입력(←, →, ↑ 반복, 8번째마다 Space)을 Tk 이벤트 큐로 전달, 20초
- 이벤트 루프 정지: 10 ms 주기 `after()` 탐침의 실제 실행 간격 (간격이 길수록 그동안 입력·그리기가 멈춤)
- 키 입력 지연: `event_generate(when='tail')` 시점부터 앱의 키 처리기가 끝날 때까지
- 도구: `python verification/gui_probe.py <프로젝트 폴더> <결과.json> 20 <난이도>`

해석: 원본은 어려움 난이도에서 측정 시간 24.2초 동안(20초 예정이었으나 정지 때문에 늘어남) 이벤트 루프 탐침이 7번만 실행되었고(평균 2.8초마다), 키 입력은 8개만 처리되었습니다. 화면을 다시 그릴 때마다 AI 탐색 `choose()`를 3번 동기 호출했기 때문입니다. 개선 후에는 AI 탐색이 작업 스레드에서 실행되고, 그리기 코드는 저장된 결과만 사용합니다.

남은 제한: Python GIL 때문에 작업 스레드가 계산하는 동안 메인 스레드도 약간 느려집니다(측정된 최대 정지에 포함). 어려움 탐색이 최대 약 190 ms이므로 체감 영향은 작습니다.
